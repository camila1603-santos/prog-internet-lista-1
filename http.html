HTTP na prática: requisição e resposta

O que é o HTTP?

HTTP (HyperText Transfer Protocol, ou Protocolo de Transferência de Hipertexto) é o protocolo que define as regras de comunicação entre o navegador e o servidor na Web. Sempre que você digita um endereço, clica em um link ou envia um formulário, o navegador usa o HTTP para pedir algo ao servidor, e o servidor usa o HTTP para responder.

O HTTP funciona no modelo de pedido e resposta: o navegador faz um pedido, o servidor processa e devolve uma resposta. Ele é um protocolo sem estado (stateless), ou seja, cada requisição é independente e o servidor não lembra, por conta própria, das requisições anteriores. Para manter informações entre uma página e outra (como um login), são usados recursos extras, como cookies e sessões.

Hoje a maior parte dos sites usa HTTPS, que é o HTTP com uma camada de criptografia (TLS). Isso protege os dados trocados para que não possam ser lidos ou alterados no caminho.

Cliente, servidor, requisição e resposta

Cliente: é quem faz o pedido. Na Web, normalmente é o navegador (Chrome, Firefox, Edge), mas também pode ser um aplicativo de celular ou um programa.

Servidor: é o computador que guarda os recursos (páginas HTML, imagens, arquivos CSS, dados) e fica esperando pedidos para respondê-los.

Requisição (request): é a mensagem que o cliente envia ao servidor. Ela informa o método (o que o cliente quer fazer), o caminho do recurso, a versão do HTTP, os cabeçalhos (informações extras) e, às vezes, um corpo com dados.

Resposta (response): é a mensagem que o servidor devolve ao cliente. Ela traz a versão do HTTP, um código de status (dizendo se deu certo ou não), os cabeçalhos e, normalmente, um corpo com o conteúdo pedido, como o HTML da página.

Resumindo o fluxo: o usuário acessa um endereço, o navegador (cliente) monta uma requisição e envia ao servidor, o servidor processa e envia a resposta, e o navegador lê essa resposta e mostra a página na tela.

Métodos GET e POST

GET: usado para buscar (ler) um recurso no servidor, sem alterar nada. É o método usado quando você digita um endereço ou clica em um link. Se houver dados, eles vão na própria URL, depois do sinal de interrogação (por exemplo: /busca?termo=html). Por isso, o GET não deve ser usado para enviar senhas ou dados sensíveis, e as URLs podem ser salvas nos favoritos e no histórico.

POST: usado para enviar dados ao servidor, geralmente para criar ou processar algo, como enviar um formulário de cadastro, fazer login ou publicar um comentário. Os dados vão no corpo da requisição, e não na URL. Uma requisição POST normalmente altera algo no servidor.

Existem outros métodos, como PUT (atualizar), DELETE (apagar) e PATCH (atualizar parte de um recurso), mas GET e POST são os mais usados em páginas web comuns.

Exemplo de requisição HTTP

Requisição GET feita pelo navegador para buscar a página inicial de um site:

Requisição Exemplo
Método GET
Caminho do recurso /index.html
Versão do HTTP HTTP/1.1
Cabeçalhos Host, User-Agent, Accept, Accept-Language...

A primeira linha tem o método (GET), o caminho do recurso (/index.html) e a versão do protocolo (HTTP/1.1). As linhas seguintes são os cabeçalhos: Host indica o site, User-Agent identifica o navegador, Accept diz o tipo de conteúdo aceito e Accept-Language diz o idioma preferido.

Requisição POST enviando os dados de um formulário de login:

Requisição Exemplo
Método POST
Caminho do recurso /login
Versão do HTTP HTTP/1.1
Cabeçalhos Host, Content-Type, Content-Length...
Corpo usuario=camila&senha=minhasenha

Aqui os dados vão no corpo, depois de uma linha em branco que separa os cabeçalhos do corpo. Content-Type diz o formato dos dados e Content-Length diz o tamanho do corpo em bytes.

Exemplo de resposta HTTP

Resposta do servidor para a requisição GET acima:

HTTP/1.1 200 OK
Date: Sat, 31 Oct 2026 14:00:00 GMT
Server: Apache
Content-Type: text/html; charset=UTF-8
Content-Length: 120

<!DOCTYPE html>
<html>
<head><title>Exemplo</title></head>
<body><h1>Olá, mundo!</h1></body>
</html>

A primeira linha (linha de status) tem a versão do protocolo (HTTP/1.1), o código de status (200) e uma mensagem curta (OK). Depois vêm os cabeçalhos: Date é a data da resposta, Server identifica o servidor, Content-Type diz que o conteúdo é HTML e Content-Length é o tamanho do corpo. Após a linha em branco vem o corpo, com o HTML que o navegador vai mostrar.

Códigos de status HTTP

O código de status é um número de três dígitos que indica o resultado da requisição. O primeiro dígito mostra a categoria: 1xx = informação, 2xx = sucesso, 3xx = redirecionamento, 4xx = erro do cliente, 5xx = erro do servidor.

200 OK: a requisição deu certo e o servidor devolveu o que foi pedido. É a resposta mais comum, por exemplo quando uma página abre normalmente.

301 Moved Permanently: o recurso mudou de endereço para sempre. O servidor informa o novo endereço no cabeçalho Location e o navegador vai até ele automaticamente. Usado, por exemplo, quando um site troca de domínio.

302 Found: o recurso está temporariamente em outro endereço. O navegador é redirecionado, mas o endereço original continua valendo. Usado, por exemplo, para mandar o usuário para a tela de login e depois de volta.

400 Bad Request: o servidor não entendeu a requisição porque ela está mal formada ou com dados inválidos, como um formulário enviado com informações no formato errado.

403 Forbidden: o servidor entendeu a requisição, mas se recusa a atender porque o cliente não tem permissão para acessar aquele recurso, como uma área restrita a administradores.

404 Not Found: o recurso pedido não existe no servidor. Acontece quando a URL está errada ou a página foi removida.

500 Internal Server Error: aconteceu um erro inesperado no servidor e ele não conseguiu completar a requisição. O problema não é do usuário, e sim do servidor, como um erro no código do site.

Conclusão

O HTTP é a base da comunicação na Web. Toda página que abrimos é resultado de uma troca de mensagens: o cliente envia uma requisição dizendo o que quer, e o servidor devolve uma resposta com um código de status e o conteúdo. Entender esse processo ajuda a desenvolver sites e a descobrir o que deu errado quando algo não funciona.
